理发预约系统需求分析与设计

一、系统概述

本系统是一个基于 uni-app 与 uniCloud 构建的多角色理发预约系统，项目名称为“剪约”。系统面向理发门店的线上预约、到店核验、服务执行、评价反馈和门店运营管理等业务场景，支持用户端、理发师端和管理员端协同工作。系统采用前后端一体化云开发模式，前端以 Vue + uni-app 实现多端界面，后端以 uniCloud 云函数承载业务逻辑，数据库采用 uniCloud MongoDB。

从项目现有代码结构来看，系统已经形成了较完整的业务闭环，覆盖认证注册、门店展示、预约下单、订单状态流转、评价售后、通知消息、理发师排班、管理员审核与运营看板等核心功能，具备作为毕业论文“系统分析与设计”章节的实际工程支撑。

二、系统建设目标

1. 为用户提供便捷的线上理发预约服务，减少线下排队和电话预约带来的沟通成本。
2. 为理发师提供排班管理和订单处理能力，提高接单与服务执行效率。
3. 为门店管理员提供订单核验、理发师审核、门店资料管理和运营统计能力，提升门店数字化管理水平。
4. 建立从预约创建、到店核验、服务开始、服务完成、评价售后到通知反馈的全流程闭环。
5. 利用统一权限控制、审计日志、状态机约束和数据索引机制，保证系统安全性、可追溯性与稳定性。

三、可行性分析

1. 技术可行性
本项目采用 uni-app 实现“一套代码多端运行”，可以同时覆盖 App 与 H5 端。后端使用 uniCloud 云函数，减少了传统服务器部署与运维成本。数据库 Schema、索引、种子数据和云函数均已在仓库中给出，说明系统技术方案成熟，具备较强的落地性。

2. 经济可行性
系统基于云开发架构，开发环境简单，部署成本较低。前端、后端和数据库统一在同一技术生态中完成，降低了开发工具链复杂度与维护开销，适合作为中小型门店预约管理系统。

3. 运行可行性
系统界面围绕预约业务设计，角色分工明确。用户只需完成注册、选店、选服务、选理发师和选时段即可完成预约；门店管理员和理发师在各自角色入口中处理业务，操作路径清晰，适合实际门店场景。

四、系统角色分析

1. 普通用户
普通用户是系统的核心服务对象，主要使用功能包括注册登录、浏览门店信息、查看服务项目、选择理发师、在线预约、订单查询、取消或改期、服务后评价、发起售后、查看通知及使用 AI 服务顾问。

2. 理发师
理发师主要负责配置自己的排班计划、查看当日订单、在顾客到店后开始服务、服务完成后结束订单。理发师角色需要和具体门店绑定，并且其服务能力由管理员进行配置。

3. 管理员
管理员负责门店后台管理，包括门店资料维护、理发师审核、理发师管理、订单核验、订单处理、售后回复、评价管理和运营数据查看。管理员在业务上承担门店运营者和系统审核者双重职责。

五、业务需求分析

（一）用户端功能需求

1. 用户注册与登录
系统需要支持用户注册、账号密码登录、忘记密码、手机号绑定与个人资料修改。登录成功后应返回 token，并将用户身份、角色和资料缓存到本地，以支持应用重启后的会话恢复。

2. 门店浏览与查询
系统需要支持门店列表展示、门店详情查看、评分展示、营业时间查看、价格区间查看以及门店评价浏览。根据代码实现，门店模块还支持关键字搜索、最低评分筛选、价格筛选等查询能力。

3. 在线预约
用户应能够从门店详情进入预约页面，选择门店服务项目、理发师、日期和时间段，并提交预约。系统应自动校验服务是否属于当前门店、理发师是否属于当前门店、理发师是否具备该服务能力、所选时间是否满足排班与营业时间要求，以及该时段是否已被占用。

4. 订单管理
用户可以查看自己的订单列表与订单详情，并依据订单状态执行取消、改期、删除等操作。系统中的订单状态机为 BOOKED、ARRIVED、IN_SERVICE、FINISHED、CANCELLED、NO_SHOW，其中用户可操作的节点主要集中在 BOOKED、CANCELLED 和 FINISHED 阶段。

5. 评价与售后
服务完成后，用户可以提交评分和文字评价，也可以查看和删除自己的评价。若服务过程中出现问题，用户还可以发起售后申请，填写问题类型与详细描述，等待门店处理。

6. 通知与消息
系统应支持预约成功、改期、取消、爽约、开始服务、完成服务等业务通知，并允许用户查看通知列表、阅读通知详情、标记已读和删除通知。App 端还具备系统通知轮询能力，用于提升重要业务消息的触达率。

7. AI 服务顾问
系统预留了 AI 服务顾问页面和对应云函数，可用于根据用户需求推荐服务项目，为系统提供智能化扩展空间。

（二）理发师端功能需求

1. 排班管理
理发师应能够设置某一天的工作开始时间、结束时间及休息时段。系统根据排班数据生成可预约时段，并在预约成功后锁定相应 time_slots 数据。

2. 订单查看
理发师需要查看自己当日的预约订单及其状态，以便安排服务节奏。

3. 服务流转
理发师在确认顾客已由管理员核验到店后，才能将订单状态从 ARRIVED 变更为 IN_SERVICE；服务结束后，可将订单状态更新为 FINISHED。系统通过状态机限制非法跳转，确保业务顺序正确。

（三）管理员端功能需求

1. 理发师审核
系统支持理发师申请后由管理员审核，审核结果包括通过和拒绝，并记录审核理由、审核时间和审核人信息。

2. 门店资料管理
管理员可以修改所属门店的名称、地址、封面、标签、营业时间、预约须知、取消规则和改期规则等信息。

3. 理发师与服务配置
管理员可以维护门店理发师信息，并配置每位理发师可提供的服务项目，实现“理发师-服务”能力绑定。

4. 到店核验
顾客预约成功后会生成 6 位核验码。管理员在顾客到店时输入核验码，将订单状态从 BOOKED 变更为 ARRIVED。该功能可以有效约束无到店确认就直接开始服务的业务漏洞。

5. 订单运营管理
管理员可以查看门店订单列表，跟踪订单状态，并在需要时进行爽约标记等管理操作。

6. 售后与评价管理
管理员可以查看门店售后申请，并对售后内容进行回复和处理；同时也可以查看门店评价数据，辅助优化服务质量。

7. 运营看板
系统支持按日或按周查看门店运营统计数据，包括预约量、服务完成率等指标，为门店经营分析提供数据支持。

六、非功能需求分析

1. 安全性需求
系统需要实现登录认证和角色鉴权。根据云函数公共模块 auth.js 的实现，系统采用 token 鉴权机制，通过 auth_tokens 集合校验令牌有效性，并在 requireRole 中执行角色检查，防止未授权访问。数据库 schema 多数关闭了前端直接读写权限，要求必须通过云函数访问，以保证数据安全。

2. 一致性需求
预约业务要求订单状态、时段锁定、事件日志和审计日志保持一致。项目中在创建订单时采用“先写订单，再锁时段，失败则回滚订单”的策略，并同步写入 order_items、order_events 和 audit_logs，体现了较强的数据一致性设计。

3. 性能需求
系统需要在移动端提供较流畅的使用体验。项目在前端引入了多级缓存策略：门店信息使用本地持久化缓存，订单列表和详情使用短期内存缓存，运营看板和时段查询也设置了缓存时间，以降低重复云函数调用次数。数据库端配置了用户订单、门店订单、理发师订单、核验码、通知和售后等索引，满足常见查询性能需求。

4. 可维护性需求
系统采用“页面层 + API 层 + 云函数层 + 公共模块层 + 数据模型层”的分层结构。公共能力统一沉淀到 sb-common 模块，降低了业务云函数重复代码，便于后期维护和扩展。

5. 可扩展性需求
系统已预留 AI 顾问、通知、审计日志、评价回复等扩展点，且数据库将订单主表、订单明细、事件日志拆分建模，有利于未来扩展多服务项订单、消息推送和数据统计分析功能。

七、系统总体设计

（一）总体架构设计

本系统采用前后端分离但一体化云开发的三层架构，可概括为表现层、业务逻辑层和数据层。

1. 表现层
表现层由 uni-app 前端页面和通用组件组成，主要负责界面展示、用户交互、表单提交和状态反馈。系统页面按角色划分为用户端、理发师端和管理员端。组件层包括导航栏、底部标签栏、弹窗、确认框和日期选择器等公共组件。

2. 业务逻辑层
业务逻辑层由 api/*.js 和 uniCloud 云函数共同构成。前端 API 层负责统一调用云函数、处理返回值、错误转换和缓存失效；云函数层负责真正的业务校验和数据写入，包括订单创建、核验、开始服务、完成服务、取消、改期、评价、售后、通知和管理员管理等业务。

3. 数据层
数据层由 uniCloud MongoDB 数据集合组成，核心集合包括 users、stores、services、orders、order_items、order_events、reviews、aftersales、barber_schedules、time_slots、notifications、auth_tokens 和 audit_logs 等。数据库通过 schema 文件约束字段结构，通过 index 文件提高查询性能。

（二）模块划分设计

1. 认证与权限模块
负责用户注册、登录、身份识别、角色分流、手机号绑定和个人资料修改，同时控制用户、理发师、管理员访问不同业务页面和云函数。

2. 门店展示模块
负责门店列表、门店详情、门店服务和门店评价的展示，并支持搜索、筛选和排序。

3. 预约下单模块
负责用户创建预约、校验服务与理发师关系、检查排班和营业时间、锁定时段并生成订单。

4. 订单流转模块
负责订单从 BOOKED 到 ARRIVED、IN_SERVICE、FINISHED 的状态变化，也负责取消、改期、爽约和删除等异常流程处理。

5. 评价与售后模块
负责用户评价、门店评分更新、售后申请、售后处理和评价管理。

6. 排班与时段模块
负责理发师排班设置和可预约时段生成，为预约业务提供底层时间资源管理能力。

7. 通知模块
负责业务通知生成、通知列表查询、已读标记、删除和 App 前台轮询提醒。

8. 运营管理模块
负责管理员后台的订单核验、理发师审核、门店资料维护、服务配置及运营看板统计。

八、系统详细设计

（一）认证与授权设计

系统在用户登录后生成 token，并写入 auth_tokens 集合。前端将 token、user 和 role 持久化到本地缓存中，在 App 启动时自动恢复。后续云函数调用统一从请求中读取 token，服务端通过 auth_tokens 和 users 集合校验身份有效性。角色分为 user、barber、admin 三类，不同角色只允许访问其授权业务接口。

（二）订单状态机设计

订单状态机是本系统的核心设计之一，具体流转如下：

1. 用户创建预约后，订单状态为 BOOKED。
2. 顾客到店并由管理员核验后，订单状态变为 ARRIVED。
3. 理发师开始服务后，订单状态变为 IN_SERVICE。
4. 服务结束后，订单状态变为 FINISHED。
5. 若用户主动取消，则订单状态变为 CANCELLED。
6. 若顾客未按时到店并被门店认定为爽约，则状态变为 NO_SHOW。

该状态机保证了“必须先核验到店，后开始服务”的业务顺序，避免出现未到店直接开始服务的逻辑错误。

（三）预约时段设计

系统采用 barber_schedules 与 time_slots 两级模型管理预约资源。barber_schedules 记录理发师在某日的工作区间和休息时间；time_slots 记录可预约的具体时段及其是否被占用。创建订单时系统根据服务时长计算需要占用的多个 5 分钟时段，并执行并发安全的时段锁定。若锁定失败，则回滚已创建的订单，保证订单与时段状态一致。

（四）门店与服务设计

stores 集合用于保存门店名称、地址、联系方式、标签、营业时间、预约规则、评分和地理位置等信息；services 集合用于保存门店服务项目，包括服务名称、价格、时长和描述。系统在订单创建阶段会将门店名称、理发师名称、服务名称和价格写入订单快照字段，避免后续门店资料修改影响历史订单展示。

（五）理发师审核与服务能力设计

users 集合除了存储普通用户，还用于存储理发师和管理员信息。对于理发师，系统增加了 pendingRole、approvalStatus、approvalReason、serviceIds、intro 等字段，支持理发师申请审核和服务能力绑定。管理员审核通过后，理发师才能正式进入业务流程。

（六）评价与售后设计

reviews 集合用于保存用户对订单的多维评分、评价内容、图片和商家回复等信息。评价提交后，系统会联动更新门店评分缓存。aftersales 集合用于记录售后类型、用户描述、门店回复和处理状态，实现从问题提交到商家处理的闭环。

（七）通知设计

notifications 集合记录用户通知，通知类型包括预约成功、改期、取消、爽约、到店提醒、开始服务和完成服务等。系统前端在 App.vue 中通过轮询机制同步关键通知，并调用系统通知能力提示用户，从而增强重要业务状态的可感知性。

（八）审计与日志设计

系统使用 order_events 记录订单状态变化过程，使用 audit_logs 记录关键业务操作人、操作时间、结果和请求 ID。该设计既支持业务追踪，也便于后续问题定位和安全审计。

九、数据库设计

（一）主要实体

1. 用户实体 users
用于存储账号、密码摘要、角色、手机号、所属门店、审核状态和理发师服务能力等信息。

2. 门店实体 stores
用于存储门店基础信息、营业时间、预约规则、评分、标签和地理位置等数据。

3. 服务实体 services
用于存储具体服务项目，如剪发、烫染、造型等，以及价格、时长和描述。

4. 订单实体 orders
用于存储预约订单主体信息，是系统最核心的数据实体，包含用户、门店、理发师、服务、预约时间、核验码和状态等字段。

5. 订单明细实体 order_items
用于存储订单中的服务明细，便于后续扩展多项目订单。

6. 订单事件实体 order_events
用于存储订单状态变化日志。

7. 评价实体 reviews
用于存储用户评分、评价内容、图片和回复信息。

8. 售后实体 aftersales
用于存储订单售后申请及处理结果。

9. 排班实体 barber_schedules
用于存储理发师每日排班信息。

10. 时段实体 time_slots
用于存储理发师每日各预约时段的占用情况。

11. 通知实体 notifications
用于存储系统通知数据。

12. 令牌实体 auth_tokens
用于存储登录令牌及有效期。

13. 审计日志实体 audit_logs
用于存储关键操作审计信息。

（二）实体关系说明

1. 一个门店可以拥有多个服务项目。
2. 一个门店可以拥有多个理发师和管理员。
3. 一个用户可以创建多个订单。
4. 一个订单只对应一个门店、一个理发师和一个主服务项目。
5. 一个订单可以对应多条订单事件日志，也可以关联评价和售后记录。
6. 一个理发师在某一天只能有一条排班记录，但可生成多个时段记录。

十、系统运行流程设计

（一）预约下单流程

1. 用户注册并登录系统。
2. 用户浏览门店，进入门店详情页。
3. 用户选择服务项目、理发师、预约日期和开始时间。
4. 系统校验门店、理发师、服务归属关系及可预约时段。
5. 系统生成订单、核验码并锁定时间资源。
6. 系统记录订单事件和审计日志。
7. 系统向用户、理发师和管理员发送预约通知。

（二）到店服务流程

1. 用户到店后向管理员出示核验码。
2. 管理员在核验页面输入核验码。
3. 系统校验订单状态、门店归属和管理员权限。
4. 系统将订单状态更新为 ARRIVED。
5. 理发师确认到店后开始服务，将状态更新为 IN_SERVICE。
6. 服务完成后，理发师将订单状态更新为 FINISHED。

（三）售后与评价流程

1. 订单完成后，用户可进入评价页面提交评分和文字内容。
2. 如用户对服务不满意，可提交售后申请。
3. 管理员在后台查看售后内容并回复处理。
4. 系统保留评价和售后记录，支持后期管理与统计分析。

十一、系统测试与质量保障设计
